## 2026-08-11 · Dify 报 SSRF，实为 Bridge HTTP 鉴权失败

### 现象

工单跑 Dify 流水线失败，UI / Dify error 类似：

```text
Access to 'http://host.docker.internal:8787/runs' was blocked by SSRF protection.
The URL may point to a private or local network address.
```

Studio 侧常被归类为「Bridge/网络瞬时」，点「重新执行」仍复现。

### 根因

1. Dify（Docker）经 **Squid `ssrf_proxy`** 访问宿主机 Bridge：`http://host.docker.internal:8787/runs`。
2. Bridge 开启了 HTTP 鉴权（`BRIDGE_HTTP_TOKEN` / `STUDIO_BRIDGE_TOKEN`），请求未带对 Bearer → Bridge 返回 **401**。
3. Dify `core/helper/ssrf_proxy.py`：凡是经 Squid（`Via`/`Server` 含 squid）的 **401/403**，一律抛成 `ToolSSRFError`（文案即上面的 SSRF），**不区分** Squid 拒绝与上游业务 401。
4. Squid `access.log` 对应为 `TCP_MISS/401`（请求已打到 Bridge），不是 `DENIED`。

因此：**多数情况下不是 SSRF allowlist 没配好，而是 Bridge token 缺失/不一致，被 Dify 误报成 SSRF。**

### 排查

```bash
# 本机 Bridge 是否在线
curl -sS http://127.0.0.1:8787/health

# 无 token 时应鉴权失败（修复后为 400，避免再被当成 SSRF）
curl -sS -o /dev/null -w '%{http_code}\n' \
  -X POST http://127.0.0.1:8787/runs \
  -H 'Content-Type: application/json' -d '{}'

# Squid 侧看是 401 还是 DENIED
docker exec docker-ssrf_proxy-1 tail -30 /var/log/squid/access.log
```

核对：

| 项 | 期望 |
|----|------|
| `apps/studio-api/.env` 与 `apps/studio-bridge/.env` | `BRIDGE_HTTP_TOKEN` 或 `STUDIO_BRIDGE_TOKEN` **相同且非空** |
| 流水线 HTTP 节点 | Dify **Bearer** + `X-Bridge-Token:{{#start.bridge_token#}}`；Studio 启动注入 `bridge_token`。**改 DSL 后须重新导入并发布 App** |
| Dify SSRF（历史） | 已随 `deploy/dify` 移除；现仅 Studio → Bridge 本机调用 |

### 已做修复（仓库内）

- Bridge 鉴权失败改为 **HTTP 400**（body 仍为 `unauthorized`），避免再被 Dify 误判为 SSRF。
- Studio 对含 `blocked by ssrf protection` 且指向 Bridge `/runs` 的错误补充说明文案；启动 Dify 前若 `bridge_token` 为空会直接报错。
- DSL 生成：HTTP 节点改为 Dify **Bearer auth** + `X-Bridge-Token` 双通道（见 `dify-dsl.generator.ts`）。**已导入的 Dify App 需重新「导入 DSL」才会带上新鉴权。**

### 后续现象（同日）：`Request failed with status code 400`

SSRF 文案消失后，失败变为 `400`。Squid 日志为 `TCP_MISS/400`，对应 Bridge `unauthorized`。

#### 再确认（run `cca8f4a9-…` / 工单 `wo-msosyntq`）

表象：Studio 日志 `bridge_token=set`，DSL 也已对流水线记录的 `app_id=51343a85-…`（「直接代码开发」）导入并发布了 Bearer 鉴权。

真因：**流水线 `dify.enabled=false`，运行走的是全局/团队 App Key**，实际打到的是另一个 App「交付流水线（Manager + 多 Agent）」`fc9f250d-…` 的旧发布版（`2026-08-09`，HTTP 节点 `authorization: no-auth`，开始变量里甚至没有 `bridge_token`）。  
Dify 节点执行里请求头只有 `Host` / `Content-Type` / `Content-Length`，没有 `Authorization` / `X-Bridge-Token` → Bridge 回 400。

处理：

1. **推荐**：流水线启用 Dify 绑定，填写「直接代码开发」的 Workflow App API Key（与已导入 `app_id` 一致），再重新执行。  
2. 或者把团队/全局 App Key 换成已修好鉴权的那个 App 的 Key。  
3. 仅「导入 DSL」而不改绑定/Key：**不会**改变实际运行的 App。

#### 本机已做（2026-08-12）

把安装级/全局 `api_tokens` 记录从旧 App `fc9f250d-…` **改挂到** `51343a85-…`（已发布 Bearer + `bridge_token`），并清了 Redis `api_token*` 缓存。之后用全局 Key 启动会打到正确图。若 Console Token 过期，流水线级「新建 App Key + 启用绑定」仍需在设置里重新登录后再做。

## 2026-08-12 · Dify 已成功但工单一直「运行中」

### 现象

Bridge / Dify 侧节点已跑完（`workflow_runs.status=succeeded`），Studio 工单仍为 `running`；`raw_summary` 停在「已提交 Human Input」，`last_synced_at` 不再更新。

### 根因

`syncDify` 用 `syncInFlight` 串行化同步，但在锁内调用 `maybeAutoApproveHumanGate` → `decideDify` → 再次 `syncDify`。第二次拿到同一 in-flight Promise 并 `await`，与外层互相等待 → **死锁**。此后该工单所有同步都挂在同一 Promise 上。

### 修复

先结束核心同步并释放 `syncInFlight`，再在锁外做自动确认；自动确认里的再次 `syncDify` 可正常执行。
